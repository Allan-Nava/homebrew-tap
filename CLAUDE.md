# CLAUDE.md — homebrew-tap

**homebrew-tap** (`github.com/Allan-Nava/homebrew-tap`): il tap Homebrew dei progetti Allan-Nava, usato come `brew tap Allan-Nava/tap` (Homebrew taglia il prefisso `homebrew-`). È un repo di **distribuzione**, non di sviluppo: cask generati + gli script e i workflow che li generano e li validano. Zero codice applicativo, zero build. Oggi due cask: `Casks/checkfleet.rb` (CLI [checkfleet](https://github.com/Allan-Nava/checkfleet)) e `Casks/checkfleet-desktop.rb` (app Wails della stessa release).

## Regole di lavoro (SEMPRE)

- **I file in `Casks/` sono generati e NON si editano a mano.** Due sorgenti distinte, non confonderle:
  - `checkfleet.rb` → **GoReleaser**, dal repo upstream, a ogni tag `v*` (`# This file was generated by GoReleaser. DO NOT EDIT.`, commit `Brew cask update for checkfleet version vX.Y.Z`). Un fix si fa in `.goreleaser.yaml` → `homebrew_casks` e si rilascia.
  - `checkfleet-desktop.rb` → **`scripts/render-desktop-cask.sh`** di questo repo, perché GoReleaser non builda l'app desktop (lo fa `desktop.yml` upstream, che allega lo zip alla release *dopo*). Un fix si fa nel template dentro lo script, poi si rigenera.
- **Nessun bump manuale di `version`/`sha256`**: i checksum si calcolano sugli asset reali della release. A mano = install rotta con `SHA256 mismatch`.
- **MAI `git push`** — lo fa sempre l'utente. MAI `Co-Authored-By` nei commit.
- **Qui non si taggia e non c'è CHANGELOG**: versioning e release vivono nel repo del progetto. La history di questo repo è quasi interamente bot: non inquinarla con commit rumorosi.
- **Gate prima di chiudere** (cask, script o workflow toccati): `scripts/ci-place-tap.sh` + `brew style` + `brew info --cask` + `brew audit --cask --online` verdi. Se si cambia il cask desktop, rigenerarlo davvero con lo script e verificare il diff.
- **Todo → `BACKLOG.md`** (sorgente unica, id stabili `HT-n`). Gli item che vanno chiusi upstream lo dichiarano; non si "aggirano" toccando `Casks/`.
- **Le issue si generano dal backlog, non a mano**: `scripts/backlog-sync.sh` (workflow `backlog-sync.yml`) tiene una issue per ogni `HT-n` — spuntare l'item la chiude, togliere la spunta la riapre. Aprire o chiudere issue a mano crea divergenza col file. Le due issue di stato (`Fix upstream arrivato: HT-n` dal watcher, `Tap rotto: la CI dei cask è rossa` dal report della CI) passano da `scripts/gh-issue.sh`, idempotente per titolo: apre se manca, riapre se chiusa, tace se già aperta.
- **Niente segreti**: `HOMEBREW_TAP_GITHUB_TOKEN` (il token con cui GoReleaser pusha qui) è un secret della CI di checkfleet e non deve mai comparire in questo repo.
- Il README è l'unica doc user-facing: se cambiano i comandi d'installazione o si aggiunge un cask, aggiornarlo.

## Comandi

```bash
scripts/ci-place-tap.sh                          # il checkout diventa allan-nava/tap in Library/Taps
brew style --except-cops Cask/Desc,Layout/EmptyLinesAroundBlockBody allan-nava/tap
brew info --cask allan-nava/tap/checkfleet       # il cask si carica?
brew audit --cask --online allan-nava/tap/checkfleet
brew install --cask allan-nava/tap/checkfleet    # in headless: HOMEBREW_NO_REQUIRE_TAP_TRUST=1
brew reinstall --cask checkfleet                 # ri-esegue il postflight (quarantine)
brew uninstall --cask --zap checkfleet-desktop
scripts/render-desktop-cask.sh [vX.Y.Z]          # rigenera il cask desktop (default: ultima release)
scripts/backlog-sync.sh --dry-run                # anteprima del sync BACKLOG.md → issue
scripts/check-upstream-fixes.sh                  # TSV landed/pending dei fix attesi da upstream
DRY_RUN=1 scripts/gh-issue.sh ensure-open "<titolo>" body.md <label>
```

## Struttura

- `Casks/checkfleet.rb` — generato da GoReleaser: `version`, `on_macos`/`on_linux` × `on_intel`/`on_arm` con url+sha256 dei tarball della release, `binary "checkfleet"`, `livecheck { skip }`, `postflight` anti-quarantine.
- `Casks/checkfleet-desktop.rb` — generato dallo script: `app "checkfleet.app"`, `depends_on :macos`, postflight anti-quarantine sul bundle, `zap trash` sui path di `com.wails.checkfleet`.
- `scripts/render-desktop-cask.sh` — risolve l'asset `checkfleet-desktop_v*_darwin_universal.zip` della release, calcola lo sha256, verifica che il bundle sia alla radice dello zip e che il nome dell'asset combaci con l'url interpolato (`v#{version}`), poi rende il cask. Exit 2 = asset non ancora pubblicato → il workflow lo tratta come skip.
- `scripts/ci-place-tap.sh` — copia il checkout in `Library/Taps/allan-nava/homebrew-tap` (i cask fuori da un tap sono rifiutati da Homebrew).
- `scripts/check-workflows.rb` — coerenza dei workflow: ogni `needs` punta a un job esistente, ogni `needs.<job>.result` è dichiarato. Exit 1 con `::error::` per ogni problema.
- `.github/workflows/cask-ci.yml` — style + load, install su `macos-14`/`macos-13` (la versione del binario deve combaciare con quella del cask, quarantine rimossa, smoke `check tcp`), install del bundle desktop, `audit --online`. Su push/PR, lunedì, e a mano.
- `scripts/backlog-sync.sh` — parser awk di `BACKLOG.md` (item `HT-n`, milestone = sezione) + reconcile delle issue via `gh`, idempotente, `--dry-run`. Il ciclo legge gli item dal **fd 3** perché sullo stdin ci sono i comandi `gh`.
- `scripts/check-upstream-fixes.sh` — audit del cask generato: dice quali fix attesi da upstream (HT-1/HT-2/HT-7) sono atterrati. TSV `landed|pending`, exit 0 sempre.
- `scripts/gh-issue.sh` — issue idempotente per titolo (`ensure-open` / `ensure-closed`), usata dal watcher dei fix e dal report della CI. `DRY_RUN=1` per provare.
- `.github/workflows/backlog-sync.yml` — sync backlog → issue su push che toccano `BACKLOG.md`/lo script/il workflow, e a mano.
- `.github/workflows/desktop-cask.yml` — rigenera e committa il cask desktop: `repository_dispatch` (`checkfleet-desktop-release`, da attivare upstream — HT-5), cron ogni 6h, manuale con tag. Valida prima di pushare, `concurrency: tap-write`, `pull --rebase` + retry.

## Trappole note / regole tecniche

- **I cask devono stare in un tap**: `brew info --cask ./Casks/x.rb` → "Homebrew requires casks to be in a tap". Perciò in locale e in CI si passa da `scripts/ci-place-tap.sh` e si usano i token (`allan-nava/tap/<cask>`), non i path.
- **`brew style` ignora un `.rubocop.yml` del tap**: forza `--config $(brew --prefix)/Library/.rubocop.yml`. Le due esclusioni (`Cask/Desc` per il `desc` che inizia con un articolo, `Layout/EmptyLinesAroundBlockBody` per il template GoReleaser) vivono nei workflow come `--except-cops`, con puntatore a `HT-2`.
- **MAI `brew style --fix`, e `brew style` sempre sui file `Casks/*.rb`, mai sul tap**: passato un tap, Homebrew stila anche gli script con shellcheck+shfmt, e quel formatter **tronca l'heredoc** di `render-desktop-cask.sh` — il cask reso perde tutto ciò che sta dopo `postflight do` (verificato). Gli script si controllano con shellcheck normale (job dedicato in `cask-ci.yml`, che con le impostazioni di default è verde: SC2250/SC2292 sono cop opzionali che solo Homebrew abilita).
- **Togliere un job da un workflow senza togliere i suoi riferimenti rende l'intero workflow invalido**: GitHub non segnala "job mancante", registra un run `failure` **senza nessun job e senza log** (successo: rimosso `shellcheck`, il job `report` lo aveva in `needs` → run 30241681227 morto). Prima di committare: `scripts/check-workflows.rb` (gira anche in CI dentro il job `shellcheck`).
- **Un commento che inizia con `# shellcheck` viene letto come direttiva** (SC1073 "Couldn't parse this shellcheck directive"): se si vuole *nominare* shellcheck in un commento, non metterlo come prima parola. Le SC2016 in `backlog-sync.sh` sono disattivate apposta — i backtick lì sono markdown per il corpo della issue, non command substitution.
- **Il `postflight` con `xattr -dr com.apple.quarantine` è VOLUTO** in entrambi i cask: niente firma né notarizzazione, senza quello Gatekeeper blocca binario e bundle. Non "sistemarlo". Per il CLI si cambia in `hooks.post.install` upstream.
- **`livecheck { skip "Auto-generated on release." }` è voluto**: la versione la spinge la release (GoReleaser per il CLI, `desktop-cask.yml` per l'app). Un livecheck sarebbe una seconda fonte di verità.
- **`depends_on macos: ">= :high_sierra"` non si può usare**: quella forma è deprecata e la versione è sotto il minimo supportato → il cask non si carica più. Nel cask desktop serve il `depends_on :macos` nudo, che è anche quello che pretende il cop `Homebrew/OSDependsOn` per i cask con artifact `app`.
- **Un cask con solo `binary` NON è macOS-only**: `Cask::Artifact::Binary` non è in `MACOS_ONLY_ARTIFACTS`, quindi `checkfleet` si installa anche su Linuxbrew 6+ e il ramo `on_linux` del cask generato è reale (il postflight `xattr` si auto-salta lì). L'app desktop invece è macOS-only per via dell'artifact `app`.
- **Un commit locale divergente rompe la release upstream**: GoReleaser pusha qui durante la release; se `main` ha commit che conflittano, quella release fallisce a metà. Tenere il repo allineato a `origin/main`.
- Aggiungere un nuovo progetto al tap si fa **dal progetto**: `homebrew_casks` nel suo `.goreleaser.yaml` con `repository: {owner: Allan-Nava, name: homebrew-tap}` + secret `HOMEBREW_TAP_GITHUB_TOKEN`. Non creando il file a mano qui.
